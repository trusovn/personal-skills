# Verification Design: SIDE-004 — Organization policy and its consumers

Check that a shared project policy supplies usable placement rules and that
implementation and independent review resolve it without losing portability,
bounded scope, or advisory metric treatment.

## Cases

| Case | Setup and action | Expected result and observation |
|---|---|---|
| V-01 | Read the new policy against AC-01's ten recommendations and controller example. Follow its map and background links. | Each recommendation has actionable applicability and exceptions; mandatory rules and advisory triggers are distinct. Examples include a cohesive extension, distinct concern and harmful split. Candidate controller boundaries are explicitly future investigation, with transactions and interfaces unresolved. Document review only. |
| V-02 | Target has an organization policy and module guidance. Add a same-kind acceptance decision using existing acceptance facts and owner. Apply each consumer's instructions to this input. | Implementation reads local authority before placement and explains retention; review accepts coherent growth when ownership stays clear, without a numerical cutoff. Source-guided worked case, not executed agent behavior. |
| V-03 | Same target; add a new process-session lifecycle to an acceptance module. Compare retention with a session owner composed by the CLI. | Implementation explains the distinct owner, placement and dependencies before editing; a necessary new file is allowed. Review examines helpers/consumers and asks for a bounded owner correction if unrelated state is retained. No legacy cleanup is imposed. Source-guided worked case. |
| V-04 | Proposed extraction moves acceptance rules into a new module but imports controller state or receives its entire namespace as a context bag. | Both consumers reject the reverse dependency under mandatory local policy, explain the maintenance consequence and seek explicit facts/dependencies with a coherent transaction owner. Smaller functions or a retention claim do not discharge this check. Source-guided worked case. |
| V-05a | Target has no standalone policy; only existing task/module authority. | Both skills continue within existing authority; neither imports this source checkout's policy nor manufactures a policy. Existing dependency-free eval targets provide this control. Instruction/expectation inspection, not executed agent behavior. |
| V-05b | Task explicitly routes equivalent organization guidance elsewhere in the target. | Both consumers honor that authority; conflicting material architecture authority returns to its owner. Source-guided resolution check. |
| V-06 | Inspect installer membership, guide, shared-file list, README and existing installer tests. Install source profile into a fresh disposable Git repository with a project-owned policy and unrelated sentinel. Check, refresh there and check again. | Both skill packages and guide match source; local policy and unrelated bytes survive; source policy is not copied to a target lacking it. Active installation remains unchanged. This exercises actual filesystem distribution, not agent judgment. |
| V-07 | Run owning installer suite, then repository aggregate; inspect architecture, registry and drift constituents separately. | Executed tests/checks retain exact outcomes and skips. Expected active-install drift is reported as failure/drift rather than waived or repaired. Metric measurement is N/A for documentation/expectation-only changes. |

## Evidence ownership and limits

Implementation owns document/reference inspection, source-guided worked cases,
disposable installation and focused-to-aggregate checks. Reuse existing eval
targets and preparation; do not introduce a generic harness or live provider.
Fresh discovery independently corroborates V-01–V-07 against submitted bytes;
separate acceptance decides conformance. Maintainability precedes registry
synchronization where applicable. Live/model execution requires separate budget
approval and remains unqualified; neither valid links nor expectation strings
prove agent compliance. Installer execution qualifies only distribution behavior.
