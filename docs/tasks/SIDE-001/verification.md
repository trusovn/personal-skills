# Verification Design: SIDE-001 — Readable verification cases

Check that a reader can find the situation, action, expected result and reason
for each case before reading document metadata. Preserve the exact proof
obligations and safe preparation routes.

## Shared setup

Use the existing lifecycle eval fixture and its import brief for the example.
Use the current skill source and preparation-contract suite for instruction
checks. These checks and a manually authored example do not qualify model output.

## Verification cases

### V-01 — Read concrete cases before metadata

**Situation:** A verification design is made for the lifecycle import brief.
**Action:** Read the opening and each case in order.
**Expected result:** A short behavior explanation comes first. Concrete titles
and Situation, Action, Expected result, Why test this and How to check fields
(or an equally clear table/sequence) explain the checks. Test methods appear
beside their cases. Common setup is stated once. There is no required opening
Testing approach table, generic Implementation handoff, or Ready means paragraph.
Source/revision information and coverage map appear at the end.
**Why test this:** Readers need to understand the promised behavior before
processing workflow metadata.
**How to check:** Review the example against AC-01–AC-04 and the source brief;
compare instruction, example and completion checks. Record whether the example
was manually authored or generated by a separately approved live eval.

### V-02 — Keep every import obligation visible

**Situation:** The lifecycle brief requires first import, interruption/resume,
invalid-header and missing-manifest refusal, and a three-item inclusive limit.
**Action:** Compare the example's cases and coverage map with that brief.
**Expected result:** Distinct IDs and exact expected results remain visible for
first import, the first committed item and next resume invocation, both refusal
guards with other prerequisites satisfied, and two/three/four items (success,
success, too_many_items). Names, bytes, unchanged destination and no duplicates
are observable where required. Limits of evidence stay beside affected claims.
**Why test this:** A simpler layout must not collapse separate failure modes.
**How to check:** Trace each AC and finite-risk row to explicit cases and inspect
the existing lifecycle eval expectations. Instruction checks alone do not prove
that an agent will produce these results.

### V-03 — Preserve safe consumers and existing artifacts

**Situation:** Consumers use Source brief declarations, revision information,
complete coverage and task-design/preflight routing.
**Action:** Inspect the source diff, consumers, existing tests/evals, installer
mapping, managed guide and README references. Run the owning focused suite and
required repository checks.
**Expected result:** One Source brief declaration and required revisions remain.
Stable IDs, conflict refusal, authority, coverage and readiness rules remain.
No runtime or plan-contract change is introduced. The T-001.2 verification file
and active .agents installation remain byte-identical. Installer references need
changes only if made stale; source content edits alone do not change ownership.
**Why test this:** Presentation changes must not weaken assurance or rewrite history.
**How to check:** Review the scoped diff and compare protected bytes with Git;
run `python3 -B -m unittest discover -s tests -p test_task_preparation_contracts.py`,
`PYTHONDONTWRITEBYTECODE=1 python3 -m unittest discover -s tests -p test_architecture.py`,
and `python3 tools/check_contracts.py --root .`. Run focused installer tests if
managed resources/references change. A model eval needs separate approval.
